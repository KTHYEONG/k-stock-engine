## 2. Top Technical Decisions (상세 6대 의사결정)

### ADR-001: JSON 전체 스냅샷에서 WAL 모드 SQLite3 영수증 카탈로그로 전환

* **Decision**:  
  수집된 원시 데이터(Bronze)의 영수증 상태 관리를 기존의 단일 JSON 파일 스냅샷 방식에서 WAL(Write-Ahead Logging) 모드가 활성화된 로컬 SQLite3 데이터베이스(`ReceiptCatalog`)로 전면 교체함.
* **Why**:  
  기존 방식은 114,833행의 카탈로그를 매 수집마다 통째로 디스크에 다시 쓰면서 488개 리비전과 23GB에 달하는 막대한 디스크 I/O를 낭비함. 또한 멀티프로세스 동시 수집 시 파일 쓰기 경합으로 데이터 갱신 유실(Race Condition)이 빈번히 발생함.
* **Trade-off**:  
  텍스트 파일 기반의 직관적인 직접 열람(Inspection) 편의성은 감소하였으나, 디스크 사용량을 **39.8MB로 99.8% 압축**하고 30초 비지 타임아웃과 단일 트랜잭션 원자적 커밋으로 동시성 무결성을 100% 보장함.

---

### ADR-002: 실시간 DART 접수시각 기반 Point-in-Time(PIT) 데이터 모델링

* **Decision**:  
  재무제표 데이터의 반영 시점을 분기말(예: 1분기 3월 31일)이 아닌, 금융감독원 DART 시스템에 실제 접수·수리된 타임스탬프(`available_at`) 기준으로 고정하고, `AsOfTable`의 이진 탐색(`bisect_right`)을 통해 쿼리하도록 강제함.
* **Why**:  
  분기 실적은 분기 종료 후 45일의 공시 유예 기간을 거쳐 시장에 공개됨. 공시 기준일로 데이터를 소급해 백테스트할 경우 미래의 실적을 과거 시점에 이미 알고 매매하는 전형적인 미래 참조 편향(Look-ahead Bias)이 발생하여 실거래 시 백테스트 수익률이 완전히 붕괴됨.
* **Trade-off**:  
  공시 접수 시각 파싱, 정정 공시 이력 추적 및 시점별 유효 데이터 분할을 위한 정규화 파이프라인의 연산 복잡도가 증가함. 그러나 실거래 환경과 100% 동일한 시점의 정보만을 공급하여 백테스트와 실거래 간 괴리(Divergence)를 원천 차단함.

### ADR-003: 부동소수점 배제, 전 계좌 정수 원장 및 매도 우선 체결 원칙

* **Decision**:  
  모든 현금 잔고, 매매 대금, 증권거래세, 위탁 수수료, 주식 수량을 순수 정수(`int`) KRW 단위로 처리하는 `Integer KRW Ledger`를 구현하고, 일별 리밸런싱 집행 시 매도 주문을 매수 주문보다 항상 선순위로 정렬(`_submission_order`)함.
* **Why**:  
  부동소수점(`float64`) 연산은 1원 미만의 반올림 오차를 지속적으로 누적시켜 실제 증권사 계좌와의 잔고 불일치를 유발함. 또한 한국 주식 시장의 T+2 거래소 결제 주기 상 매도 대금이 입금되기 전에 매수 주문이 먼저 전송되면 잔고 부족으로 인한 주문 거부나 미수금(Overdraft) 사고가 발생함.
* **Trade-off**:  
  비율 기반의 목표 포트폴리오 산출 후 정수 주식 수로 변환할 때 내림(`math.floor`) 처리에 따른 미세한 현금 완충금(0.5% Cash Buffer)이 발생함. 반면 금융 회계 오차 0원과 장중 미수금 발생 가능성을 0건으로 완벽 차단함.

### ADR-004: 레거시 호환 계층(Shims) 폐기 및 단일 실행 계약(Single Contract) 통일

* **Decision**:  
  구버전 백테스터 및 과거 데이터 파이프라인에 대한 호환 계층을 일절 유지하지 않고, `legacy/` 디렉터리로 완전히 격리 후 프로덕션 코드베이스를 최신 계약(`src/core`, `src/storage`, `src/integrations`, `src/data`, `src/execution`, `src/backtest`)으로 단일화함.
* **Why**:  
  과거 실험 코드와 신규 엔진이 얽혀 전체 코드 라인 수가 42.8k에 달했고, 개발자가 코드를 수정할 때 어떤 경로가 프로덕션에 실제 영향을 미치는지 파악하기 어려워 유지보수 비용과 인지 부하가 극심했음.
* **Trade-off**:  
  과거 리서치 스크립트와의 하위 호환성이 완전히 단절되었음. 그러나 핵심 코드베이스 크기를 **17.7k LOC(58.6% 감축)**로 슬림화하고, 987개의 전수 단위/통합 테스트를 단 25.29초 만에 100% 완벽 검증할 수 있는 극도의 엔지니어링 민첩성을 확보함.

### ADR-005: 영속 쿼터 원장(`ProviderQuotaStateStore`) 도입 및 보수적 속도 제약

* **Decision**:  
  외부 공급자(DART, 브로커 OpenAPI) 호출을 관리하기 위해 임시 파일 원자적 교체(`os.replace`) 기반의 영속 쿼터 원장을 구축하고, 초당 5건(최소 간격 0.2초)의 보수적인 안전 속도로 모든 수집 워커를 제어함.
* **Why**:  
  실측 결과 DART API는 지속 15 rps까지 정상 작동했으나 30 rps 도달 시 공인 IP 단위로 즉시 연결이 차단되는 현상이 확인됨. 또한 멀티스레드 수집기 병렬 기동 시 일일 허용 쿼터(10,000~20,000건)가 비원자적 호출로 인해 조기 소진되는 위험이 존재했음.
* **Trade-off**:  
  단일 배치 수집 완료에 소요되는 절대 시간이 늘어남(예: 16,000건 수집 시 약 53분 소요). 그러나 IP 차단에 따른 전체 파이프라인 다운타임을 0건으로 통제하고, KST 자정 자동 초기화 및 다중 워커 간 잔여 쿼터 안전 공유를 달성함.

---

### ADR-006: Python AST 기반 정적 계층 의존성 강제 및 단조 래칫 정책

* **Decision**:  
  모든 소스 파일의 `import` 구문을 추상 구문 트리(AST)로 파싱하여 허용된 계층 의존성(`ALLOWED`) 외의 상위 계층 참조 및 격리된 `legacy/` 패키지 침범을 검증하는 기계적 테스트를 구축함.
* **Why**:  
  문서상으로만 정의된 아키텍처 규칙은 팀 규모 확장이나 AI 에이전트의 코드 변경 과정에서 쉽게 침해되며, 순환 참조나 계층 간 결합도 증가를 사전에 방지할 수 없음.
* **Trade-off**:  
  새로운 패키지나 예외적인 교차 참조가 필요할 경우 아키텍처 테스트 파일을 명시적으로 수정해야 함. 그러나 기존의 예외 사항(`KNOWN_VIOLATIONS`)이 오직 줄어들기만 허용하는 래칫(Ratchet) 정책을 통해 기술 부채의 재유입을 0건으로 동결함.
